# Site localisation

[Русский](i18n.md) · **English**

How the English and Chinese versions of the public site are built, what we
translate, what the customer translates, and why the decisions are what they are.

Task: [issue #54](https://github.com/michaelwelly/MuseonUrania/issues/54),
stage 4 of the [roadmap](../operations/roadmap.en.md).

---

## 1. Three languages, the same three the assistant already knows

Three languages: Russian, English, Chinese. Codes: `ru`, `en`, `zh`.

This is not a new register of languages. Vedalina is already split across three
of them in the `Guardrails` class (`backend/assistant`), where `enum Speech`
holds exactly `RU`, `EN` and `ZH` and the language of a question is decided by
script — Cyrillic, Han characters, everything else. The interface deliberately
follows the same model.

Introducing `en-US` and `zh-CN` here would give us two disagreeing registers of
languages inside one product, and the question "why does the assistant answer in
English while the page stays Russian" would become a question about code
mapping.

The `lang` attribute on `<html>` is nevertheless full: `ru`, `en`, `zh-Hans`.
A bare `zh` leaves the browser to choose between simplified and traditional
script, and font selection depends on that choice.

## 2. URLs: a prefix in the path, Russian at the root

| Language | Home | Catalogue |
| --- | --- | --- |
| Russian | `/` | `/products/` |
| English | `/en/` | `/en/products/` |
| Chinese | `/zh/` | `/zh/products/` |

**Why not a subdomain.** `en.vedal-med.ru` needs its own certificate, its own
DNS record and its own build. A prefix needs none of that: the site stays one
application. The project has a single domain and it is not connected yet —
setting up three for the sake of translation means paying for the split before a
single translated paragraph exists.

**Why Russian has no prefix.** The addresses `/products/` and `/about/` have
been circulating in the catalogue, in the presentation and in letters to the
customer for a month and a half. Moving to `/ru/` would turn every one of those
links into a redirect. The Russian version is the leading one (rule 3 in
`CLAUDE.md`), so it stays at the root. `/ru/products/` deliberately does not
exist and answers 404: a second address with identical content is a duplicate
for search engines.

## 3. Layout in the code

```
frontend/
├─ lib/i18n.ts              language codes, localePath, stripLocale, hreflang
├─ lib/content-i18n.ts      falling back to the Russian original
├─ lib/lang-preference.ts   precedence rule: whose language wins
├─ lib/intl-route.ts        parsing the [lang] segment, rejecting foreign codes
├─ content/ui.ts            INTERFACE dictionary, three languages
├─ content/translations.ts  CONTENT dictionary, filled in by the customer
├─ components/SiteShell.tsx shell: <html lang>, header, footer, widgets
├─ components/LanguageSwitcher.tsx  switcher in the header
├─ components/LangPreference.tsx    remembered choice and auto-detection
├─ components/TranslationNotice.tsx notice about untranslated content
├─ app/(site)/                  Russian version, root without a prefix
│  └─ <section>/screen.tsx      page body, shared by every language
│  └─ <section>/page.tsx        thin wrapper: lang = "ru"
└─ app/(intl)/[lang]/           English and Chinese versions
   └─ <section>/page.tsx        thin wrapper: lang comes from the URL
```

**Why two root layouts.** The `lang` attribute on `<html>` must change with the
page language, and `<html>` is rendered by the root layout. Nesting a `[lang]`
segment inside the existing `app/(site)/layout.tsx` is not possible — the nested
layout would render a second `<html>` inside the first. So the translated
versions get their own root layout in the `(intl)` group. This is a documented
Next pattern, and the project already uses it: the admin area `app/(admin)` is a
root layout too.

The price is known: switching between the Russian and English version is a full
page load, not a client-side navigation. For a language change that is
appropriate — the entire page changes, header and footer included.

**Why `screen.tsx` rather than `page.tsx`.** Two routes render the same page
body. Next validates what a `page.tsx` file exports, and extra exports break the
build — while the shared body needs to export both a component and a metadata
function. `screen.tsx` is not a route filename, so that restriction does not
apply to it.

## 4. We translate the interface, the customer translates the content

This is a condition of the task, not a developer's decision:

> Interface translations are kept separate from content translations: we
> translate the interface, the customer translates the content.

| | Interface | Content |
| --- | --- | --- |
| What it is | navigation, buttons, field labels, states, column headers, accessibility labels | product descriptions, specifications, registration statuses, document titles, news texts, legal wording |
| Where it lives | `content/ui.ts` | `content/translations.ts` |
| Who translates | we do | the customer, through approval |
| What is missing | nothing: the type demands all three languages, a forgotten key fails to compile | every translation; the dictionaries are empty |
| If a translation is missing | impossible | the Russian original is shown, marked `lang="ru"` |

**Why we do not translate content ourselves.** The content rules (`CLAUDE.md`)
forbid inventing specifications, certificates, registration status, delivery
terms and clinical claims. Translating such wording produces a new edition of
it: "регистрационное удостоверение" and "registration certificate" are not
legally the same thing, and "ожидает уточнения" rendered as "pending" reads as
"being processed" — that is, as a promise.

**How the fallback works.** `contentText(lang)` returns two functions: `t(ru)`
gives the approved translation or the Russian original, and `mark(...ru)`
returns `"ru"` or `undefined` — the value for the `lang` attribute of the
element holding that text. The mark is mandatory: without it the browser, the
screen reader and the built-in translator all treat a Russian paragraph as
English.

A notice sits at the top of the page (`TranslationNotice`): product
descriptions, specifications and document statuses are shown in Russian, the
translation has not been approved yet. Showing Russian text silently on an
English page is not acceptable — it looks like a fault rather than a translation
awaiting approval.

**The key of the translation dictionary is the Russian text itself**, not an
invented identifier. An identifier drifts silently: the customer edits the
Russian wording, the key stays the same, and the old translation keeps showing —
meaning an unpublished claim stays live on the English page. Keying by the
original closes that by construction: change the Russian text and there is no
translation for it, so the page shows the new Russian, and updating the
translation becomes a visible action.

## 5. How the language is chosen

Precedence:

```
the visitor's choice > a prefixed URL > the browser language > Russian
```

1. **A prefixed URL** is an explicit request for that language. We never redirect
   away from it, and we remember it: the next visit to the root opens in the same
   language.
2. **A remembered choice** applies only to Russian URLs, that is, where the
   language is not stated. A remembered "Russian" is a choice too, and it turns
   auto-detection off.
3. **The browser language** (`navigator.languages`) is read only when no choice
   has been made yet. Auto-detection deliberately does not write a choice into
   storage: otherwise it would be indistinguishable from a decision made by a
   person.

The visitor's choice is kept in `localStorage` under the key `vedal.lang` and
survives a reload. Without it, a visitor who switched to Russian would get
English again on every new page.

**Why auto-detection lives in the browser and not in middleware.** The customer
asked for the language to be picked up from the browser, and the direct way is
Next middleware reading `Accept-Language`. That breaks architecture property
number one ([PROJECT.md](../PROJECT.en.md), 5.3): "a backend failure does not
take the site down" — pages are baked into static files at build time and served
ready-made, while middleware puts a server step in front of every request to
every page. To detect a language we would have made the whole site depend on a
live server.

A crawler that does not run scripts sees the Russian page with `hreflang` next
to it — and it already knows how to pick a version by the language of the query.

## 6. Search engines

- **`hreflang`** sits in the metadata of every page: `ru`, `en`, `zh-Hans` and
  `x-default`. The fallback is Russian because it is complete. Without
  `hreflang`, three addresses with the same meaning read as duplicates, and the
  translated versions either compete with the Russian one for the same results
  or drop out of them.
- **`canonical`** is per version and points at that version.
- **The sitemap** carries all three languages, and every entry declares
  `alternates.languages` with all three addresses. The repetition is deliberate:
  a search engine takes the relationship between versions from whichever source
  it reads first, and it reads the sitemap before the pages.
- There is no per-language sitemap: the page sets do not diverge, the translated
  versions mirror the Russian one page for page.

## 7. The browser's built-in translator

The customer named it as a cheap substitute: "pages should translate properly
with Google Translate". The translator has three conditions and all three hold:
`<html>` carries `lang`, neither `translate="no"` nor `notranslate` appears
anywhere, and text is not hidden in images or drawn on a canvas.

The `lang="ru"` mark on untranslated fragments helps here too: the built-in
translator sees that the paragraph is Russian and translates exactly that.

The distinction below matters and the customer has to settle it:

- **The visitor's browser translates** — that is their action and their
  responsibility, we publish nothing.
- **We publish a translation** — that is our text, and it goes through approval
  alongside the Russian.

Betting on the translator means the visitor will read product specifications and
wording from registration documents in machine translation.

## 8. What is left

- **Content translations.** The dictionaries in `content/translations.ts` are
  empty. The first line added there appears on the page with no code change.
- **Language for portal content.** Product descriptions, news and documents come
  from the database and have no language field — translating a product card will
  require a column in `product`, `news`, `document` and a dimension in the public
  API. That is backend work.
- **The Vedalina widget.** The assistant answers in the language of the question
  (`Guardrails`), but the chat window's interface and the quick-reply buttons
  arrive from the portal in Russian.
- **The cookie notice.** The consent text is legal wording and we cannot
  translate it ourselves; it is currently shown in Russian with a `lang` mark.
- **The admin area** is single-language and stays that way: it is the workplace
  of a Russian-speaking company's staff.
