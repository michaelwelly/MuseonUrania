# Автодеплой стенда из main

**Русский** · [English](autodeploy.en.md)

## Что это

Машина сама проверяет, не изменился ли `main`, и разворачивает стенд, если
изменился. Триггер тот же, что у обычного CI-деплоя — пуш в `main`, — но
направление обратное: не GitHub идёт на сервер, а сервер спрашивает GitHub.

## Почему не деплой с GitHub Actions

Обычный путь — workflow на раннере GitHub ходит на сервер по SSH. Здесь он
не годится по двум причинам, и каждой хватило бы отдельно.

**Репозиторий публичный.** Self-hosted раннер на публичном репозитории GitHub
прямо не рекомендует: workflow из форка выполняется на машине, и присланный
кем угодно pull request превращается в выполнение чужого кода — на той же
машине, где живёт боевой `c3ag.ru`.

**Диапазон адресов раннеров огромен и меняется.** Деплой с раннеров GitHub
требует открыть SSH под весь их пул. Для машины с чужим боевым сайтом это
несоразмерная плата за удобство.

Инверсия снимает обе проблемы сразу:

- наружу не открыт ни один дополнительный порт;
- в GitHub не лежит ни одного секрета и ни одного ключа от сервера;
- чужой код на машине не выполняется — скрипт сравнивает два хеша и зовёт
  уже существующий `deploy-stand-prod.sh`.

Цена: правка доезжает до стенда не мгновенно, а в пределах двух минут, и
журнал деплоя лежит на машине, а не во вкладке GitHub.

## Что ставится

| Файл в репозитории | Куда на машине |
| --- | --- |
| `scripts/autodeploy.sh` | `/opt/vedal-portal/scripts/autodeploy.sh` |
| `scripts/deploy-stand-prod.sh` | `/opt/vedal-portal/scripts/deploy-stand-prod.sh` |
| `scripts/vedal-autodeploy.service` | `/etc/systemd/system/vedal-autodeploy.service` |
| `scripts/vedal-autodeploy.timer` | `/etc/systemd/system/vedal-autodeploy.timer` |

Сам деплой — `deploy-stand-prod.sh` — до сентября 2026 лежал только на машине,
как untracked-файл. Ровно тот кусок системы, который на минуты ронял сайт при
каждой выкатке, нельзя было ни прочитать, ни отревьюить, ни откатить: чтобы
узнать, что он делает, надо было зайти по SSH. Теперь он в репозитории, и
`/opt/vedal-portal` — это тот же рабочий каталог, куда деплой делает
`git reset --hard`. То есть отдельная установка ему не нужна: машина забирает
новую версию скрипта вместе с кодом.

Из этого следует одна тонкость, ради которой в скрипте есть перезапуск с копии
во временном каталоге: `git reset --hard` переписывает файл, который в этот
момент выполняется. bash читает скрипт по смещению, и подмена на ходу — это
выполнение середины нового файла с середины старого. Скрипт первым делом
копирует себя в `/tmp` и работает оттуда, так что переписывать можно.

## Установка

Один раз, от пользователя с правом `sudo`:

```bash
cd /opt/vedal-portal
git fetch origin main && git checkout main && git pull

sudo install -m 755 scripts/autodeploy.sh /opt/vedal-portal/scripts/autodeploy.sh
sudo install -m 644 scripts/vedal-autodeploy.service /etc/systemd/system/
sudo install -m 644 scripts/vedal-autodeploy.timer   /etc/systemd/system/

sudo mkdir -p /var/lib/vedal-autodeploy
sudo chown ubuntu:ubuntu /var/lib/vedal-autodeploy

sudo systemctl daemon-reload
sudo systemctl enable --now vedal-autodeploy.timer
```

## Проверка

```bash
# таймер включён и когда сработает в следующий раз
systemctl list-timers vedal-autodeploy.timer

# прогнать прямо сейчас, не дожидаясь таймера
sudo systemctl start vedal-autodeploy.service

# что произошло
journalctl -u vedal-autodeploy -n 50 --no-pager
```

В журнале на каждый запуск ровно одна из строк:

- `main не менялся (abc12345) — деплой не нужен`;
- `новый main: abc12345 → def67890, разворачиваю` и следом `готово`;
- `предыдущий деплой ещё идёт — пропускаю`;
- `выкатка заморожена с <когда> (<причина>) — пропускаю`;
- `деплой упал с кодом N — отметка не обновлена, повторю в следующий раз`.

## Заморозка на время показа

```bash
echo "показ заказчику" > /opt/vedal-portal/var/deploy-freeze   # перед показом
rm /opt/vedal-portal/var/deploy-freeze                          # после
```

Пока файл есть, автодеплой ничего не разворачивает и пишет в журнал, с какого
момента и почему. Отметка о развёрнутом коммите при этом не ставится: заморозка
откладывает выкатку, а не отменяет её — снимут файл, и накопившийся `main`
приедет сам.

Зачем выключатель, если есть договорённость «не катить во время показа».
Затем, что катит не человек, а таймер, и о показе он не знает. Договорённость,
которая живёт только в голове, на показе не работает: достаточно, чтобы кто-то
влил свою ветку в `main` из другой комнаты.

Ручной запуск `deploy-stand-prod.sh` заморозку не проверяет — это осознанно:
выключатель останавливает автоматику, а не человека, который знает, что делает.

## Как выкатка перестала ронять сайт

Домен отдаёт внешний nginx соседа по машине; его upstream —
`172.17.0.1:18080`, то есть порт, опубликованный контейнером шлюза. Пока
контейнер шлюза пересоздаётся, порт не держит никто, и сосед на каждый запрос
получает `connection refused` и отдаёт посетителю 502.

Прежняя версия деплоя делала всё одной командой:

```bash
docker compose ... up -d --build --remove-orphans
```

и окно получалось не «пока пересоздаётся шлюз», а «пока поднимается весь
стек».

Причина — в том, в каком порядке compose делает две половины пересоздания.
Старый контейнер он снимает СРАЗУ, в начале `up`, а новый запускает в порядке
зависимостей — то есть шлюз стартует только после того, как портал стал
`healthy`, а тот накатывает миграции и поднимает Spring. Между этими двумя
моментами порт 18080 не держит никто. Минуты, а не секунды — 8 сентября
владелец портала попал ровно в это окно и полчаса искал поломку, которой
не было.

Проверено на модели (docker compose v5, две службы, зависимая публикует порт,
зависимость становится здоровой за десяток секунд):

| Как выкатывать | Окно, когда порт не отвечает |
| --- | --- |
| одной командой `up -d` | 11 c — весь `up` целиком |
| по шагам с `--no-deps`, как теперь | 1 c — только своё пересоздание |
| по шагам, зависимая служба не менялась | окна нет, контейнер не тронут |

Там же проверено, что пересоздание зависимости само по себе зависимую службу
не трогает: пока меняется только портал, шлюз стоит как стоял.

Теперь порядок разобран руками, и каждый шаг идёт с `--no-deps`, то есть без
каскада:

| Шаг | Что делает | Порт 18080 |
| --- | --- | --- |
| 1 | собирает образы | держит старый шлюз |
| 2 | поднимает инфраструктуру (`db`, `kafka`, `keycloak`, `connect`) | держит старый шлюз |
| 3 | пересоздаёт `portal`, ждёт `healthy` | держит старый шлюз |
| 4 | пересоздаёт `site`, ждёт `healthy` | держит старый шлюз |
| 5 | трогает `api-gateway` — и то не всегда | здесь и только здесь возможно окно |

Шаг 5 — единственный, который может освободить порт. `up -d` пересоздаёт
контейнер, только если изменился образ или конфигурация сервиса; правка в
`backend/app` или `frontend/` шлюза не касается, и compose честно ничего не
делает. То есть **в типичной выкатке порт 18080 не освобождается вообще**, и в
журнале про это есть строка: `шлюз не менялся — порт 18080 не освобождался`.

### Почему пятый шаг раньше срабатывал всегда

Одного порядка для этого не хватило. Пересборка **без единой правки** давала
новый id образа: buildx по умолчанию кладёт в образ provenance-аттестацию, а в
ней — время сборки. Все слои при этом `CACHED`, но манифест другой, и id
другой. Для compose новый id образа значит «сервис изменился», то есть
пересоздать контейнер.

Отсюда и получалось, что каждая выкатка пересоздавала шлюз — даже когда правка
была в одном файле фронтенда. Видно поимённо: 8 сентября `vedal-gateway`,
`vedal-portal` и `vedal-site` пересозданы в одну и ту же секунду, хотя менялся
не весь стек.

Лечится одной переменной, она выставлена в скрипте перед сборкой:

```bash
export BUILDX_NO_DEFAULT_ATTESTATIONS=1
```

Проверено обоими способами: повторная сборка без правок даёт байт в байт тот же
id и compose оставляет контейнер в покое, а при настоящей правке в исходниках
контейнер по-прежнему пересоздаётся. Теряется при этом только подпись о
происхождении в метаданных образа — здесь она не нужна: образ собирается на той
же машине, где запускается, и никуда не публикуется.

Сборка вынесена отдельным шагом до всего остального. Она и раньше шла первой
(`up --build` собирает, потом пересоздаёт), но теперь упавшая сборка сообщает
об этом словами: `стек не тронут, работает прежняя версия`.

Чего это не чинит, честно:

- когда меняется сам `api-gateway`, окно остаётся. Один порт нельзя отдать двум
  контейнерам сразу, и подмена без разрыва требует своего прокси перед шлюзом.
  Но окно — это старт одного Spring Boot, десятки секунд, а не минуты;
- пока пересоздаётся `site` (шаг 4), главная страница не отдаётся. Разница
  в том, что отвечает на неё шлюз своей ошибкой, а не отказ соединения: сосед
  проксирует наш ответ, а не синтезирует 502.

## Что остаётся за внешним nginx

Заглушка вместо ошибки. Пока окно есть — хоть и короткое, — посетитель в него
видит ошибку, а не страницу «идёт обновление». Сделать заглушку на нашей
стороне нельзя: домен отдаёт nginx соседа, и это его конфигурация. Строка,
которую надо добавить в `server`-блок `vedal-med.ru`, одна:

```nginx
error_page 502 503 504 /maintenance.html;
location = /maintenance.html {
    root /var/www/vedal;
    internal;
}
```

и рядом положить сам `maintenance.html`. Правит это владелец машины: чужой
конфиг мы не трогаем.

Без этой правки наша часть всё равно даёт главное — окно из минут превратилось
в десятки секунд, а в типичной выкатке исчезло совсем.

## Как это ведёт себя при сбоях

Проверено прогоном до установки, все четыре случая:

**Деплой упал.** Отметка о развёрнутом хеше не обновляется, и следующий запуск
повторит попытку. Это главное свойство: запиши отметку до сборки — упавший
деплой считался бы успешным, стенд остался бы на старом коде, а журнал
сообщал бы, что всё в порядке.

**GitHub недоступен.** Скрипт выходит с ошибкой и ничего не трогает; стенд
продолжает работать на том, что развёрнуто.

**Запуски наложились.** Сборка идёт минуты, таймер срабатывает чаще. Второй
запуск видит занятый лок и штатно пропускает ход — в журнале это строка
«занято», а не падение.

**Сборка упала.** Ни один контейнер не тронут: сборка идёт до пересоздания
отдельным шагом. В журнале — `стек не тронут, работает прежняя версия`.

**Контейнер не стал здоровым.** Деплой останавливается на этом шаге, кладёт
в журнал последние 60 строк логов контейнера и выходит с ошибкой. Дальше
работает предохранитель: три подряд неудачи на одном коммите — и автодеплой
перестаёт пытаться, вместо того чтобы пересобирать стенд каждые две минуты.

**`flock` отсутствует.** Отдельная проверка до всего остального, потому что
без неё `if ! flock -n 9` не отличает «лок занят» от «команды нет»: скрипт
писал бы «предыдущий деплой ещё идёт», выходил с нулём и навсегда перестал
бы разворачивать стенд, ежеминутно отчитываясь об успехе.

## Что остаётся ручным

Откат. Скрипт разворачивает то, что лежит в `main`, и не умеет возвращаться
назад. Откат — это `git revert` в `main`: через две минуты стенд сам приедет
на прежнее состояние. Так у отката остаётся след в истории, чего не даёт
ручное переключение веток на машине.
