# Автодеплой стенда из main

**Русский** · [English](autodeploy.en.md)

## Что это

Машина сама проверяет, не изменился ли `main`, и разворачивает стенд, если
изменился. Триггер тот же, что у обычного CI-деплоя — пуш в `main`, — но
направление обратное: не GitHub идёт на сервер, а сервер спрашивает GitHub.

## Почему не деплой с GitHub Actions

Обычный путь — workflow на раннере GitHub ходит на сервер по SSH. Здесь он
не годится по двум причинам, и каждой хватило бы отдельно.

**Репозиторий публичный.** Self-hosted раннер на публичном репозитории GitHub
прямо не рекомендует: workflow из форка выполняется на машине, и присланный
кем угодно pull request превращается в выполнение чужого кода — на той же
машине, где живёт боевой `c3ag.ru`.

**Диапазон адресов раннеров огромен и меняется.** Деплой с раннеров GitHub
требует открыть SSH под весь их пул. Для машины с чужим боевым сайтом это
несоразмерная плата за удобство.

Инверсия снимает обе проблемы сразу:

- наружу не открыт ни один дополнительный порт;
- в GitHub не лежит ни одного секрета и ни одного ключа от сервера;
- чужой код на машине не выполняется — скрипт сравнивает два хеша и зовёт
  уже существующий `deploy-stand-prod.sh`.

Цена: правка доезжает до стенда не мгновенно, а в пределах двух минут, и
журнал деплоя лежит на машине, а не во вкладке GitHub.

## Что ставится

| Файл в репозитории | Куда на машине |
| --- | --- |
| `scripts/autodeploy.sh` | `/opt/vedal-portal/scripts/autodeploy.sh` |
| `scripts/vedal-autodeploy.service` | `/etc/systemd/system/vedal-autodeploy.service` |
| `scripts/vedal-autodeploy.timer` | `/etc/systemd/system/vedal-autodeploy.timer` |

## Установка

Один раз, от пользователя с правом `sudo`:

```bash
cd /opt/vedal-portal
git fetch origin main && git checkout main && git pull

sudo install -m 755 scripts/autodeploy.sh /opt/vedal-portal/scripts/autodeploy.sh
sudo install -m 644 scripts/vedal-autodeploy.service /etc/systemd/system/
sudo install -m 644 scripts/vedal-autodeploy.timer   /etc/systemd/system/

sudo mkdir -p /var/lib/vedal-autodeploy
sudo chown ubuntu:ubuntu /var/lib/vedal-autodeploy

sudo systemctl daemon-reload
sudo systemctl enable --now vedal-autodeploy.timer
```

## Проверка

```bash
# таймер включён и когда сработает в следующий раз
systemctl list-timers vedal-autodeploy.timer

# прогнать прямо сейчас, не дожидаясь таймера
sudo systemctl start vedal-autodeploy.service

# что произошло
journalctl -u vedal-autodeploy -n 50 --no-pager
```

В журнале на каждый запуск ровно одна из строк:

- `main не менялся (abc12345) — деплой не нужен`;
- `новый main: abc12345 → def67890, разворачиваю` и следом `готово`;
- `предыдущий деплой ещё идёт — пропускаю`;
- `деплой упал с кодом N — отметка не обновлена, повторю в следующий раз`.

## Как это ведёт себя при сбоях

Проверено прогоном до установки, все четыре случая:

**Деплой упал.** Отметка о развёрнутом хеше не обновляется, и следующий запуск
повторит попытку. Это главное свойство: запиши отметку до сборки — упавший
деплой считался бы успешным, стенд остался бы на старом коде, а журнал
сообщал бы, что всё в порядке.

**GitHub недоступен.** Скрипт выходит с ошибкой и ничего не трогает; стенд
продолжает работать на том, что развёрнуто.

**Запуски наложились.** Сборка идёт минуты, таймер срабатывает чаще. Второй
запуск видит занятый лок и штатно пропускает ход — в журнале это строка
«занято», а не падение.

**`flock` отсутствует.** Отдельная проверка до всего остального, потому что
без неё `if ! flock -n 9` не отличает «лок занят» от «команды нет»: скрипт
писал бы «предыдущий деплой ещё идёт», выходил с нулём и навсегда перестал
бы разворачивать стенд, ежеминутно отчитываясь об успехе.

## Что остаётся ручным

Откат. Скрипт разворачивает то, что лежит в `main`, и не умеет возвращаться
назад. Откат — это `git revert` в `main`: через две минуты стенд сам приедет
на прежнее состояние. Так у отката остаётся след в истории, чего не даёт
ручное переключение веток на машине.
