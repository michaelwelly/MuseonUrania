# VEDAL stand-prod: периметр и точки входа

Дата фиксации: 2026-08-27.

Стенд живёт на общей ВМ `smart_soultion_mvp` с публичным IP `51.250.31.97`.
На этой же машине остаются C3AG/Astor, поэтому VEDAL пока вынесен на отдельные
порты, без захвата `80` и `443`.

## Что открыто наружу для VEDAL сейчас

| Назначение | Адрес | Кому нужен | Комментарий |
| --- | --- | --- | --- |
| Публичный сайт и API | `http://51.250.31.97:18080` | посетители, заказчик, команда | Главная точка входа стенда. Через неё работают страницы, формы, Ведалина и Swagger. |
| Keycloak для входа сотрудников | `http://51.250.31.97:18180` | сотрудники и команда | Временно открыт до появления домена и HTTPS. Нужен браузеру: без публичного issuer админка не сможет завершить логин. |
| SSH | `51.250.31.97:2222` | Михаил, Егор, автодеплой/операторы | Держать только по точным IP или через VPN. Сейчас рабочий операторский source IP: `31.184.215.189/32`. |

## Как заходят сотрудники

На текущем стенд-проде сотрудники идут в админку по адресу
`http://51.250.31.97:18080/admin/` и нажимают вход через рабочую учётную
запись. Браузер переходит в Keycloak на `http://51.250.31.97:18180`, после
успешного входа возвращается обратно в `/admin/`.

Эта схема нужна только до подключения домена. Для реальной эксплуатации с
персональными данными вход сотрудников должен работать по HTTPS:

- `https://vedal-med.ru/admin/` — интерфейс админки;
- `https://auth.vedal-med.ru` или `https://vedal-med.ru/auth` — Keycloak;
- `18180` закрывается снаружи после настройки reverse proxy и сертификатов.

Пароли, токены, клиентские секреты, S3-ключи и учётные записи сотрудников не
передаются в рабочих чатах. После переноса домена и выдачи рабочих доступов
временные пароли надо заменить.

## Что использует Ведалина

| Поток | Нужно открыть наружу? | Деталь |
| --- | --- | --- |
| Виджет на сайте → API | Да, через `18080` | `POST /api/assistant/v1/chat` и `POST /api/assistant/v1/ask`. |
| Backend → YandexGPT | Нет входящего порта | Нужен исходящий HTTPS из ВМ к `llm.api.cloud.yandex.net`. |
| Backend → PostgreSQL/Kafka | Нет | Внутри docker network. |
| Публичные медиа | Не порт ВМ | `https://storage.yandexcloud.net/vedal-media/...`. Бакет предназначен для открытых фото и медиа. |
| Документы | Через API/индексацию портала | На текущем этапе приватного корпуса нет: всё, что есть на сайте и загружается в S3 для VEDAL, считается материалом публичного корпуса и должно попадать в индекс/RAG Ведалины. |

На MVP-этапе источник знаний Ведалины один: опубликованные страницы сайта,
карточки продукции, новости, документы и файлы, загруженные в S3 как материалы
VEDAL. Если заказчик позже передаст действительно закрытые документы, это будет
отдельный режим с отдельной политикой доступа, а не текущее поведение.

Подробная схема загрузки и индексации описана в
[vedalina_rag_pipeline.md](vedalina_rag_pipeline.md).

## S3/Object Storage

| Бакет | Назначение | Публичность |
| --- | --- | --- |
| `vedal-media` | фото, фоновые изображения, открытые медиа сайта | можно отдавать публично для сайта |
| `vedal-documents` | документы и файлы карточек VEDAL | на MVP все загружаемые сюда материалы считаются индексируемыми для Ведалины; прямой листинг бакета можно держать закрытым, отдачу и индексацию делает портал |
| `c3ag-media` | медиа соседнего проекта C3AG | не относится к VEDAL |

Важно: закрытый прямой доступ к бакету не равен закрытому документу. Бакет может
не показывать список файлов наружу, но портал всё равно читает его по сервисному
ключу, публикует разрешённые ссылки и добавляет содержимое в RAG.

## Swagger

Сейчас Swagger доступен через стенд:

- `http://51.250.31.97:18080/swagger-ui/index.html`
- `http://51.250.31.97:18080/v3/api-docs/vedal-public`
- `http://51.250.31.97:18080/v3/api-docs/vedal-admin`

Для текущей разработки это удобно: Михаил, Егор и интеграции видят контракт API.
Перед настоящим production-переносом надо выбрать один из вариантов:

1. оставить Swagger только для текущих IP команды;
2. открывать Swagger через VPN/SSH-туннель;
3. выключить публичный Swagger и хранить контракт в CI-артефактах/репозитории.

## Домен и DNS

Перед переключением основного `vedal-med.ru` безопаснее сначала попросить
доступ к DNS-зоне или временный поддомен для проверки:

- `stage.vedal-med.ru` или `new.vedal-med.ru` → `51.250.31.97`;
- снизить TTL записей до `300` секунд за несколько часов до переключения;
- не менять MX-записи почты, если переносится только сайт;
- подтвердить, кто делает финальный rollback на старый сайт, если потребуется.

Данные от почты и старой WordPress-админки не равны доступу к DNS. Для
переноса сайта нужен доступ к регистратору/Cloud DNS или действие со стороны
ответственного системного администратора.

## Целевой production-периметр

После получения доступа к `vedal-med.ru` и настройки HTTPS нормальная схема
должна стать такой:

| Назначение | Целевой адрес | Порты наружу |
| --- | --- | --- |
| Сайт, формы, публичная Ведалина | `https://vedal-med.ru` | `80`, `443` |
| Вход сотрудников | `https://auth.vedal-med.ru` или `/auth` за reverse proxy | `80`, `443` |
| Админка | `https://vedal-med.ru/admin/` | `80`, `443` |
| SSH/DevOps | VPN или точные IP на `2222` | не открывать в мир |
| PostgreSQL, Kafka, Debezium, внутренний portal | docker network | наружу не открывать |
| Object Storage | `https://storage.yandexcloud.net/vedal-media/...` и сервисный доступ к `vedal-documents` | не порт ВМ |

Тогда временный `18180` закрывается, а пароли сотрудников перестают ходить по
HTTP. До этого момента логин на стенде пригоден для проверки, но не для
массовой работы с реальными персональными данными.
