# VEDAL Portal: архитектура серверной части

Дата: 2026-08-06. Статус: согласован в обсуждении, ждёт письменного ревью.

## Рамка

Целевая картина из [брифа собственника](../../architecture/vedal_portal_owner_brief.md) —
предложение, которое ещё не принято. Строить её целиком сейчас значит писать код
под нерешённое. Поэтому спека описывает архитектуру, которая:

- закрывает то, что сдаём сейчас: сайт, бэкенд под него, админку и заготовку
  под ассистента;
- оставляет предусмотренные места для того, что появится, если предложение
  примут: CRM целиком, Keycloak, закрытый контур, ИИ-поиск по документам.

Что делаем:

1. Бэкенд под текущий сайт — каталог, новости, документы, приём заявок.
2. Админка — вход сотрудника, управление контентом, просмотр заявок.
3. Заготовка под LLM — контур Урании с ограничениями, в который вставляется модель.

Что не делаем до согласования: воронка сделок и КП, Keycloak, VPN/Zero Trust,
приватный Document Vault с ролевым доступом, VLM для сервиса и производства.

## Пять свойств, которыми меряем стабильность

Формулировки конкретные, чтобы по ним можно было проверить решение.

1. **Падение бэкенда не роняет сайт.** Каталог, новости и документы уезжают в
   статику на сборке. Живой бэкенд нужен формам и Урании.
2. **Схема меняется только миграциями.** Ручной `ALTER` на проде запрещён:
   после него дамп восстанавливается в схему, которой нет в истории.
3. **Наружу уходит только опубликованное.** Это свойство запроса, а не
   дисциплины редактора.
4. **Заявка не теряется.** Запись в базу и событие коммитятся одной транзакцией.
5. **Одна дверь на запись снаружи.** Правило проверки пишется один раз.

## Общая форма

Одно приложение Spring Boot, одна база, три входа:

| Вход | Кто ходит | Что делает |
| --- | --- | --- |
| `Public API` | сборка сайта, Урания | read-only, только опубликованное, кэшируемое |
| `Forms API` | сайт, Яндекс Форма, разбор почты | единственная запись снаружи |
| `Admin UI` | сотрудник | контент, документы, заявки; под сессией |

Четвёртой двери не заводим: новая функция приезжает в одну из трёх. Тогда
периметр проверяется в трёх местах, а не в тридцати контроллерах.

### Модули

Границы из [backend/README.md](../../../backend/README.md), плюс два новых:
`content` (новости и пресс-центр) и `assistant` (Урания).

| Модуль | Ответственность |
| --- | --- |
| `catalog` | продукция, категории |
| `content` | новости, пресс-центр |
| `documents` | метаданные документов, публикация, файлы |
| `crm` | заявки, статусы, ответственный |
| `assistant` | Урания: поиск по опубликованному, ограничения |
| `notifications` | шаблонные письма |
| `audit` | журнал, только добавление |
| `iam` | учётные записи админки, роли |
| `common` | ошибки, идентификаторы, время, outbox |

**Правило зависимостей:** модуль не импортирует другой модуль напрямую, только
его интерфейс. `crm` знает `CatalogQuery`, а не внутренности `catalog`. Это
цена, которую платим сейчас за возможность вынуть модуль в отдельный сервис
потом, не распутывая клубок.

### Порты наружу

Четыре интерфейса, у каждого простая реализация на раннем шаге и полноценная
позже. Домены не знают, что за портом; смена реализации — вопрос конфигурации.

| Порт | Ранняя реализация | Полная реализация |
| --- | --- | --- |
| `FileStorage` | локальный каталог | Yandex Object Storage |
| `MailSender` | запись в лог | SMTP Яндекс 360 |
| `LlmEngine` | детерминированный поиск | YandexGPT + pgvector |
| `EventPublisher` | запись в лог | Kafka |

Подписанные ссылки и приватность — свойство `FileStorage`, а не вызывающего
кода. Переезд на S3 не может случайно раскрыть закрытый файл.

## Контракты API

Версия в пути. Ломающее изменение — новая версия, старая живёт до перевода
потребителей.

### Public API

```
GET /api/public/v1/categories
GET /api/public/v1/products
GET /api/public/v1/products/{slug}
GET /api/public/v1/news
GET /api/public/v1/news/{slug}
GET /api/public/v1/documents
```

Отдаёт только записи с `published = true`. Ответы с `ETag` и
`Cache-Control: public, max-age=300`, чтобы повторная сборка сайта не ходила в
базу. Ошибки — `application/problem+json` (RFC 9457), один формат на все двери.

### Forms API

```
POST /api/forms/v1/leads
Idempotency-Key: <uuid>
```

Тело: тип формы (`quote | catalog | consultation | service | partner`), поля из
[Lead Form Model](../../frontend/content_model.md), согласие. Ответ `202` и
идентификатор обращения. Повтор с тем же ключом возвращает тот же ответ и не
создаёт второй лид.

Защита: лимит частоты по реальному адресу клиента, honeypot-поле, ограничение
размера тела. Авторизации нет — дверь публичная по назначению.

### Assistant API

```
POST /api/assistant/v1/ask
```

Ответ содержит текст и список источников. Если подходящих опубликованных
источников нет — ответа нет, есть передача человеку с контактами.

### Admin UI

`/admin/**`, Thymeleaf, сессия, Spring Security. Отдельный маршрут выбран
сознательно: его можно целиком закрыть на уровне прокси, не трогая приложение.

## Данные

### Первый шаг: каталог

```
category        id, slug, name, position
product         id, slug, name, kind, summary, detail,
                doc_status, published, sort_order,
                image_src, image_alt, created_at, updated_at
product_category  product_id, category_id
product_spec    id, product_id, kind, position, label, value, muted
```

`doc_status` (`confirmed | pending`) и `published` — **разные** флаги.
Первый означает «характеристики подтверждены датащитом» и рисует бейдж на
сайте. Второй означает «видно снаружи». Схлопывание их в один убирает с сайта
половину каталога.

Поля из [Product Model](../../frontend/content_model.md), которые сейчас никто
не может заполнить (сертификация, согласующий, языки, `cta_type`), не заводим —
добавим миграцией, когда появятся ответы. Пустая колонка гниёт быстрее, чем её
успевают заполнить.

Наполнение: миграция-сид переносит 13 позиций из `frontend/content/products.ts`.

### Общие таблицы

```
outbox          id, aggregate, aggregate_id, type, payload,
                created_at, published_at
audit_entry     id, at, actor, action, subject, subject_id,
                correlation_id, ip, payload
lead            id, form, name, company, phone, email, product_slug,
                message, consent_version, consent_at, source, status,
                owner, correlation_id, idempotency_key, created_at
```

`audit_entry` — только вставка: прав на `UPDATE` и `DELETE` у приложения нет.
Журнал, который можно поправить задним числом, бесполезен при разборе инцидента.

Индекс на `outbox (published_at, id) WHERE published_at IS NULL` — по нему
работает relay и считается лаг.

## События

Транзакционный outbox: строка сущности и строка события коммитятся одним
`COMMIT`. Отдельный relay читает outbox и публикует. Прямая публикация из
обработчика запрещена — между `INSERT` и отправкой есть щель, в которую
проваливаются лиды.

| Топик | Кто пишет | Кто читает |
| --- | --- | --- |
| `vedal.leads.v1` | `crm` | письма, аудит |
| `vedal.documents.v1` | `documents` | индексация, аудит |
| `vedal.notifications.v1` | `notifications` | отправка |
| `vedal.audit.v1` | все | запись журнала |

Ключ партиционирования — идентификатор сущности: события одного лида не
переставляются местами. Потребители идемпотентны, обработанные идентификаторы
лежат в таблице. Событие, которое не обрабатывается после ретраев, уходит в DLQ
и разбирается руками — иначе один битый PDF останавливает конвейер.

Kafka не источник истины и не бэкапится: всё в топиках порождено из outbox.

## Конвейер Урании

Документ, помеченный в админке как публичный, уезжает событием: извлечение
текста (PDF, при необходимости OCR) → нарезка на чанки с метаданными изделия и
языка → эмбеддинги → pgvector. Ответ собирается из найденных чанков и обязан
нести ссылки на источники.

Ограничения из [urania_assistant_spec.md](../../strategy/urania_assistant_spec.md)
живут **в сервисе над портом**, не в промпте: не диагностирует, не рекомендует
лечение, не выдумывает характеристики, цены и сроки, не показывает внутренние
документы. Модель получает только то, что мы ей отдали, — уговорить её показать
закрытый файл нельзя, потому что файла в контексте нет.

pgvector расширением к основной базе. Отдельный Qdrant — только если корпус
перерастёт, это видно по времени поиска.

## Бэкапы и восстановление

Бэкап на том же сервере — не бэкап. Бэкап, который ни разу не восстанавливали, —
гипотеза.

| Сценарий | Защита |
| --- | --- |
| Сгорела машина | Непрерывный WAL через `wal-g` в Object Storage, полный бэкап раз в неделю |
| Пропал доступ к облаку | Недельный `pg_dump -Fc`, зашифрованный, в бакет другого аккаунта |
| Бэкапы удалили | Отдельный сервисный аккаунт с правами только на запись, версионирование бакета |
| Потеряли файлы | Версионирование Object Storage; восстановление проверяется парой «дамп + состояние бакета» |

Ключ шифрования дампов — в Lockbox и в офлайн-копии: если потерян аккаунт,
потерян и Lockbox.

Проверка раз в месяц: последний дамп разворачивается в отдельную базу, на ней
прогоняются миграции и сверяются количества строк по ключевым таблицам.

Предварительные цифры, **ждут подтверждения**: допустимая потеря — 5 минут,
время подъёма — 1 час. Практически всё ценное сосредоточено в таблице `lead`;
каталог и новости воспроизводимы из репозитория.

## Наблюдаемость

- Структурные логи с `correlation_id` сквозь все слои и события.
- Метрики через Actuator.
- **Главный сигнал — лаг outbox.** Relay встал, приложение зелёное, формы
  принимаются, пользователи видят «спасибо», лиды копятся и никуда не уезжают.
  Алерт: есть записи старше 5 минут.
- Второй сигнал: последний успешный бэкап старше суток.
- Персональные данные в логи не пишем — только `correlation_id` и идентификатор
  лида. Иначе система логов тоже становится хранилищем ПДн.

## Персональные данные

Формы собирают ФИО, телефон и почту. Следствия для схемы:

- Хранить не галочку, а **версию текста согласия** и время. Через год иначе не
  доказать, с чем именно согласился человек.
- Срок хранения и автоочистка. Предварительно 3 года, **ждёт подтверждения**.
- Удаление по обращению.
- Инфраструктура в РФ — выполняется выбором Яндекса.

## Периметр

Приложение стоит за обратным прокси. Настройки, без которых оно работает
неправильно:

- `server.forward-headers-strategy=framework` и список доверенных прокси. Иначе
  лимит частоты считает всех посетителей одним клиентом, а аудит пишет адрес
  прокси вместо адреса пользователя.
- Лимит размера тела на прокси согласован с загрузкой документов, иначе PDF
  падает с 413 до приложения.
- Таймауты: длительные операции живут в асинхронном конвейере, а не в HTTP.

VPN — периметр, а не авторизация. Вход, роли и аудит в админке нужны независимо
от того, закрыта ли она по сети.

**Решение по `/admin`:** сейчас доступен из интернета за паролем и вторым
фактором; закрытие по сети — переключатель на уровне прокси, когда появится
VPN. Код от выбора не зависит.

## Доставка кода и окружения

Сборка с тестами и образом, миграции применяются на старте, деплой с graceful
shutdown — заявка, летящая в момент перезапуска, дописывается. Откат — возврат
на прошлый образ, а не «починим вперёд». Сайт при деплое не мигает: он статика.

Окружения из [infrastructure_architecture.md](../../architecture/infrastructure_architecture.md):
`prod`, `staging`, `internal`, `lab`. В `lab` — только несекретные данные.

Тесты доменов — на настоящей базе через Testcontainers, не на H2: различия
диалектов вылезают на проде, а не в тестах.

## Порядок реализации

От простого к сложному. Каждый шаг оставляет работающее приложение.

1. **`catalog`** — Postgres в Docker, Flyway, формат ошибок, тесты, публичное
   API, сид из `products.ts`, CRUD в админке.
2. **`content`** — новости той же механикой. Проверка, что шаблон повторяем.
3. **`crm` + Forms API** — приём заявок, идемпотентность, outbox, список
   заявок в админке.
4. **`notifications`** — письма из outbox, шаблоны, учёт доставки.
5. **`documents`** — метаданные, `FileStorage` на локальном каталоге,
   публикация, публичные ссылки.
6. **Kafka** — relay начинает публиковать, `audit` начинает потреблять, DLQ.
7. **`assistant`** — Урания на детерминированном поиске по опубликованному,
   ограничения в сервисе.
8. **Переезд** — Object Storage вместо каталога, Managed PostgreSQL, Managed
   Kafka, VM, бэкапы, мониторинг.

Шаги 1 и 2 не требуют инфраструктуры. Шаг 8 упирается в Yandex Cloud, которого
пока нет, — до него бэкенд живёт локально, а сайт остаётся статикой.

Восемь шагов — не один план реализации. План пишется на шаг 1; каждый
следующий получает свой, когда предыдущий закрыт.

## Решения, ждущие подтверждения

1. Допустимая потеря данных и время подъёма: предложено 5 минут и 1 час.
2. Срок хранения заявок: предложено 3 года.
3. `/admin` закрываем по сети или оставляем за паролем и MFA.
4. Где живёт объектное хранилище — вопрос открыт и в

5. Когда подключаем Keycloak — после согласования закрытого контура.
