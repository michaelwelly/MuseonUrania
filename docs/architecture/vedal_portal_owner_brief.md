# VEDAL Portal: закрытый контур и CRM

**Русский** · [English](vedal_portal_owner_brief.en.md)

Расшифровка презентации для собственника `VEDAL_owner_closed_contour_and_CRM_v1.pdf`
(8 слайдов, лежит рядом в этой папке). Материал для первого обсуждения и сбора
обратной связи.

Документ задаёт целевую архитектуру: сайт, CRM и закрытый контур — одна платформа,
а не витрина отдельно и учёт отдельно. Всё, что мы делаем во `frontend/` и
`backend/`, должно ложиться в неё.

## 1. Идея

Сайт, CRM и закрытый контур в одной управляемой архитектуре.

- **Продолжаем сайт.** Frontend, backend, формы, вход и CRM-модуль развиваются
  как единая платформа.
- **Разделяем контуры.** Открытые коммуникации остаются в Яндекс 360,
  чувствительные данные остаются внутри.
- **Даём контроль.** Лиды, сделки, документы, доступы, аудит и бюджет становятся
  прозрачными для собственника.

## 2. Сайт как вход в продажи и управление

Не отдельная витрина, а основа VEDAL Portal для клиентов и сотрудников.

| Уже согласовано | Добавляем | Что это решает |
| --- | --- | --- |
| VM и сайт с frontend/backend | CRM внутри VEDAL Portal | клиентская база не живёт в почте |
| публичный каталог и формы заявок | контролируемый gateway между системами | сделки и КП ведутся в одном месте |
| точка входа для внутреннего раздела | роли, аудит, документы и бэкапы | собственник видит управляемую картину |

Подпись под заголовком: «Нормальный пакет: уже согласованная VM и сайт
становятся основой продукта; Яндекс 360 — открытый офис; закрытые данные
управляются внутри VEDAL Portal/CRM.»

Пять вертикальных дорожек слева направо:

| Дорожка | Что внутри |
| --- | --- |
| **Пользователи** | Клиент, Продажник, Бухгалтер, Админ/ИБ, Собственник |
| **Открытый офис** — покупаем, Яндекс 360 | Почта на домене, Календарь, Телемост, Формы, Диск без секретов, Вики/Трекер для общей операционки |
| **Согласованный сайт / VM** — развиваем как продукт | Public Frontend (сайт + каталог), Lead Forms (КП / консультация / сервис), Urania public assistant (только approved content), Backend API (формы, каталог, личный вход), Admin panel / CMS, Login area (вход в закрытую CRM) |
| **DMZ / Controlled integration** — пишем под проект | Integration Gateway (webhook/API intake), Event queue, Antivirus / DLP, Manual approve, Outbound templates, Import/export audit |
| **Закрытый контур** — на VM + приватные managed-сервисы | VEDAL CRM inside site, Document Vault, PostgreSQL как источник истины, Private Object Storage, Keycloak + MFA + роли, VPN / Zero Trust, Logs + backups |

Опции закрытого контура на слайде: Lockbox, Audit Trails, WAF, Managed
PostgreSQL, Cloud Backup. Подпись у дорожки сайта: «Пишем сейчас: сайт,
backend, формы, каркас CRM и роли доступа».

Подписи на стрелках между дорожками: заявка с сайта, письмо → форма/лид,
webhook из формы, события сайта, вход сотрудника, approved lead, approved doc,
письмо по шаблону, счета/акты внутри, наружу без секретов, управление доступом,
SSO/MFA доступ, дашборд/отчёты.

Три сценария по низу слайда:

- **Продажник.** Лид приходит с сайта, формы или почты → gateway проверяет
  источник и вложения → в CRM создаётся черновик → продажник ведёт сделку и КП
  внутри закрытого контура → клиенту уходит только очищенное письмо.
- **Бухгалтер.** Вход через VPN/SSO/MFA → счета, акты, договоры берутся из
  CRM/Document Vault → ЭДО/1С/Контур подключаются как внешняя бухгалтерская
  интеграция → в CRM возвращаются статусы, номера и ссылки, а не вся финансовая
  кухня.
- **Админ и собственник.** Админ управляет пользователями, группами, доступами
  и бэкапами → собственник видит дашборд (лиды, сделки, источники, статусы) →
  инциденты разбираются по логам сайта, gateway, CRM и облачного аудита.

**Чего не было в тексте брифа:** вход строится на **Keycloak + MFA**, а не на
своей авторизации; между сайтом и CRM стоит **очередь событий**; вложения
проходят **антивирус/DLP**; перед передачей в CRM есть шаг **ручного approve**;
документы лежат в **приватном объектном хранилище**; закрытый контур закрыт
**VPN / Zero Trust**.

## 4. Что покупаем, а что пишем

Принцип: стандартные сервисы не переписываем, уникальную логику держим у себя.
Это снижает риск.

**Покупаем**

- Яндекс 360: почта, календарь, Телемост, Формы.
- Yandex Cloud: VM, backup, logging, monitoring.
- Managed PostgreSQL, Lockbox, WAF по мере готовности.

**Пишем**

- VEDAL Portal: сайт, backend, формы, вход.
- CRM: лиды, клиенты, сделки, КП, статусы.
- Integration Gateway: правила, approve, аудит.

**Не выносим наружу**

- Клиентская база и коммерческие условия.
- Договоры, счета, маржа, токены, ПДн.
- Внутренние отчёты и управленческие решения.

## 5. Путь сделки

Заявка может прийти из сайта, формы или почты, но источник истины один.

1. **Заявка.** Сайт, Яндекс Форма или корпоративная почта.
2. **Проверка.** Gateway проверяет источник, поля и вложения.
3. **Черновик лида.** CRM создаёт запись без автоматического доступа к закрытым данным.
4. **Сделка и КП.** Продажник ведёт историю, документы и статусы внутри портала.
5. **Ответ клиенту.** Наружу уходит только шаблонное письмо или согласованный документ.

Результат: меньше ручной потери лидов и меньше чувствительной информации в
открытом офисном контуре.

## 6. Роли и аудит

Для 50 сотрудников ключевой выигрыш не в сложности, а в дисциплине доступа.

**Бухгалтер**

- Входит через VPN/SSO/MFA.
- Работает со счетами, актами, договорами и статусами оплат.
- Интеграция с 1С/Контуром подключается без вывода всей финансовой кухни наружу.

**Админ / ИБ**

- Заводит сотрудников через группы и роли.
- Увольнение: блокировка SSO/VPN и отзыв сессий.
- Инциденты разбираются по логам сайта, gateway, CRM и облачного аудита.

## 8. Первый этап

Цель встречи — не финализировать детали, а получить согласие на направление.

**Решения, которые нужно принять**

1. CRM делаем внутри VEDAL Portal?
2. Какие данные запрещено хранить в Яндекс 360?
3. Кто получает доступ к CRM на первом этапе?
4. Нужна ли интеграция с 1С/Контуром сразу?

**Состав первого релиза**

- Публичный сайт и каталог.
- Backend API, формы и авторизация.
- Лиды, клиенты, сделки, КП и документы.
- Роли, аудит, бэкапы и базовый gateway.

**Рекомендация из презентации:** продолжать разработку сайта сразу как foundation
для VEDAL Portal, чтобы не переделывать архитектуру после запуска витрины.

  с проверкой источника, полей и вложений.
