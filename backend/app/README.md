# app

**Русский** · [English](README.en.md)

Точка входа Spring Boot: сборка модулей в приложение, конфигурация окружений,
миграции схемы, health-проверки.

Окружения из [infrastructure_architecture.md](../../docs/architecture/infrastructure_architecture.md):
`prod`, `staging`, `internal`, `lab`.

Здесь не должно быть доменной логики — только связывание модулей и настройки.

## Модуль сборки

`portal-app` — единственный модуль, который превращается в приложение.
Он объявляет все остальные, и его `pom.xml` читается как состав портала.

Что лежит именно здесь и почему:

- **точка входа и конфигурация окружений** — связывание, а не логика;
- **миграции Flyway.** По доменам их не разложить: база одна (следствие
  транзакционного outbox), история миграций одна, а порядок между доменами
  важен — `V14` правит `lead` и ссылается на `product` и `document`.
  Разложить их по модулям значит завести гонку номеров версий между ветками;
- **тесты, поднимающие приложение.** Им нужен собранный контекст со всеми
  модулями сразу. Чистые тесты правил остались в своих модулях: `Pipelines`
  в `crm`, `Guardrails` в `assistant`, `LocalFileStorage` в `documents`;
- **сводный отчёт покрытия.** Классы лежат в двенадцати модулях, а тесты,
  которые их проходят, — здесь; мерять помодульно значит получить
  одиннадцать нулей и одну сотню.

Собранный jar называется `app/target/portal.jar` — без версии, чтобы поднятие
версии не требовало правки `Dockerfile`.
