# Backend

Серверная часть VEDAL Portal. Java + Spring.

Состав модулей выведен из [брифа собственника](../docs/architecture/vedal_portal_owner_brief.md):
сайт, CRM и закрытый контур — одна платформа. Стандартные сервисы (почта, облако,
БД) покупаем, уникальную логику пишем сами.

## Состав первого релиза

Бриф определяет первый релиз так: публичный сайт и каталог; backend API, формы и
авторизация; лиды, клиенты, сделки, КП и документы; роли, аудит, бэкапы и базовый
gateway. Плюс два модуля из
[спеки архитектуры](../docs/superpowers/specs/2026-08-06-vedal-portal-architecture-design.md),
которых в исходном списке не было, — `content` и `assistant`. Итого одиннадцать:

| Модуль | Назначение |
| --- | --- |
| [app](app/) | Сборка Spring Boot, конфигурация, точка входа |
| [common](common/) | Общие типы, ошибки, валидация, outbox, лимиты частоты |
| [iam](iam/) | Пользователи, роли, доступ |
| [catalog](catalog/) | Продукция и категории, публичное API для сайта |
| [content](content/) | Новости и пресс-центр |
| [documents](documents/) | Документы, статусы публикации, объектное хранилище |
| [gateway](gateway/) | Приём заявок с сайта: проверка, approve, передача в CRM |
| [crm](crm/) | Лиды, клиенты, сделки, КП |
| [notifications](notifications/) | Письма клиентам и уведомления менеджерам |
| [assistant](assistant/) | Урания: ответы по опубликованному, жёсткие ограничения |
| [audit](audit/) | Журнал действий и доступа к документам |

Код каждого — в `src/main/java/ru/vedal/portal/<модуль>/`. Папки рядом с этим
файлом остаются документацией границ.

## Путь заявки

Он же определяет границы модулей. Из брифа:

```
Заявка (сайт, форма, почта)
  → gateway     проверяет источник, поля и вложения
  → crm         создаёт черновик лида без доступа к закрытым данным
  → crm         сделка, КП, документы, статусы внутри портала
  → notifications  наружу уходит только шаблонное письмо
```

Каждый шаг пишет в `audit`.

## Что отложено

Папок пока нет:

- **knowledge** — внутренний AI-поиск по документации, этап 3 в [роадмапе](../docs/operations/roadmap.md).
- **vlm** — визуальные модели для сервиса и производства, отдельный пилот.

Отложено и внутри существующих модулей:

- **Kafka.** Шаг 6 порядка реализации из спеки. Пока потребители событий живут
  в процессе: relay раздаёт их через `DomainEventConsumer`, повторы отсекаются
  по `(потребитель, событие)`. Форма та же, что будет у консьюмера топика.
- **Переезд на инфраструктуру Яндекса.** Шаг 8. Упирается в Yandex Cloud,
  которого пока нет: Object Storage вместо локального каталога, Managed
  PostgreSQL, Managed Kafka, бэкапы, мониторинг.
- **`ETag` на публичном API.** Спека выносит его в следующий этап: на двенадцати
  позициях выигрыш нулевой, `Cache-Control` уже стоит.
- **Keycloak.** До согласования закрытого контура вход в админку — Spring
  Security с локальными учётными записями за интерфейсом `iam`.

## Что не хранится и не выносится наружу

Из брифа, раздел «Не выносим наружу»: клиентская база, коммерческие условия,
договоры, счета, маржа, токены, персональные данные. Публичное API сайта отдаёт
только каталог и согласованные документы.

## Инфраструктура

Покупаем, а не пишем: Яндекс 360 (почта, календарь), Yandex Cloud (VM, бэкапы,
логи, мониторинг), Managed PostgreSQL, Lockbox, WAF по мере готовности.

## Как запустить

Нужен только JDK 25 и PostgreSQL 16. Maven ставить не надо — в репозитории лежит
wrapper.

**База.** Либо контейнером:

```
docker compose -f backend/compose.yaml up -d
```

либо нативной установкой PostgreSQL 16 на порт 5434 с ролью и базой `vedal`.
Адрес, пользователь и пароль переопределяются переменными `VEDAL_DB_URL`,
`VEDAL_DB_USER`, `VEDAL_DB_PASSWORD`; значения по умолчанию совпадают с
`compose.yaml`. Схему ведёт только Flyway, миграции применяются на старте.

**Приложение.**

```
cd backend
./mvnw spring-boot:run
```

Первый администратор создаётся, только если заданы обе переменные — иначе
учётной записи просто не будет:

```
VEDAL_ADMIN_USER=editor VEDAL_ADMIN_PASSWORD=<пароль> ./mvnw spring-boot:run
```

Приложение поднимается на `http://localhost:8081`. Порт не 8080, потому что на
машине разработки он занят чужим контейнером.

## Что уже работает

Три двери из спеки: публичное чтение, единственная запись снаружи, админка.

| Маршрут | Кто ходит | Что делает |
| --- | --- | --- |
| `GET /actuator/health` | мониторинг | живость; остальные endpoint'ы закрыты |
| `GET /api/public/v1/categories` | сборка сайта | категории каталога |
| `GET /api/public/v1/products` | сборка сайта | только опубликованные позиции, `Cache-Control: max-age=300` |
| `GET /api/public/v1/products/{slug}` | сборка сайта | карточка изделия; неопубликованное — 404 |
| `GET /api/public/v1/news` | сборка сайта | лента; пусто — это `[]`, а не ошибка |
| `GET /api/public/v1/news/{slug}` | сборка сайта | публикация; неопубликованная — 404 |
| `GET /api/public/v1/documents` | сборка сайта | перечень со статусом доступа; ссылка на файл только у опубликованных |
| `GET /api/public/v1/documents/{slug}/file` | посетитель | файл; закрытый — 404, обращение пишется в журнал |
| `POST /api/forms/v1/leads` | формы сайта | приём заявки, заголовок `Idempotency-Key`, ответ `202` |
| `POST /api/assistant/v1/ask` | Урания | ответ по опубликованному со ссылками; нет источников — передача человеку |
| `GET /admin/products` | сотрудник | каталог: правка и публикация |
| `GET /admin/news` | сотрудник | новости: создание, правка, публикация |
| `GET /admin/documents` | сотрудник | документы: загрузка файла и публикация по согласованию |
| `GET /admin/leads` | сотрудник | заявки |

Ошибки всех дверей — `application/problem+json` (RFC 9457). У форм и ассистента
свои лимиты частоты по адресу клиента.

## Что закрыто ограничениями базы, а не кодом

Правила, которые нельзя обойти правкой контроллера или ошибкой редактора:

- `document_public_only` — внутренний и конфиденциальный документ не может стать
  публично скачиваемым;
- `document_published_has_file` — публикация без загруженного файла запрещена;
- `document_published_is_listed` — опубликованный документ обязан быть в перечне;
- `lead_idempotency_key_idx` — повтор отправки формы не создаёт вторую заявку;
- `event_consumed_idx` — повторная доставка события не приводит ко второму письму;
- `news_published_needs_date` — опубликованная новость обязана иметь дату;
- триггер `audit_entry_append_only` — журнал нельзя править задним числом.

Триггер не защищает от `TRUNCATE`: statement-триггеры на него не срабатывают.
Настоящая защита — отзыв прав `UPDATE`/`DELETE`/`TRUNCATE` у роли приложения,
это шаг администратора при развёртывании среды.

## Порты наружу

Реализация меняется конфигурацией, домены за порт не заглядывают.

| Порт | Сейчас | Дальше |
| --- | --- | --- |
| `EventPublisher` | запись в лог | Kafka |
| `MailSender` | запись в лог | SMTP Яндекс 360 |
| `FileStorage` | локальный каталог `var/documents` | Yandex Object Storage |
| `LlmEngine` | детерминированный поиск по словам | YandexGPT + pgvector |

Каталог наполняется миграцией `V2__catalog_seed.sql`, которая **генерируется**,
а не пишется руками:

```
node backend/tools/seed-catalog.mjs > backend/src/main/resources/db/migration/V2__catalog_seed.sql
```

Источник — `frontend/content/products.ts`. Править `V2` вручную бессмысленно:
перегенерировать и закоммитить заново.

## Тесты

```
cd backend
./mvnw test
```

Тесты идут на настоящем PostgreSQL через Testcontainers, поэтому **требуют
запущенного Docker**. H2 не используется: различия диалектов должны вылезать
здесь, а не на проде.

## Принятые решения

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Сборка | Maven + wrapper | Скучный стандарт, wrapper снимает установку Maven с машины |
| Java | 25 | В системе стоит JDK 25, Spring Boot 4.1 её поддерживает |
| Число сервисов | Одно приложение | 50 сотрудников; модули — границы пакетов `ru.vedal.portal.*`, а не отдельные деплои |
| Раскладка кода | `backend/src/main/java/ru/vedal/portal/<модуль>/` | Стандартный Maven-layout; папки `app/`, `crm/`… рядом остаются документацией модулей |

Spring Boot 4.1.0 на Spring Framework 7. Подключены: webmvc, validation,
actuator, data-jpa, flyway, security, thymeleaf; Jackson 3.

Три ловушки Boot 4, на которые здесь уже наступили:

- **Flyway подключается через `spring-boot-starter-flyway`,** а не через один
  `flyway-core`. Автоконфигурации в Boot 4 разнесены по модулям: с одним
  `flyway-core` миграции не применяются **молча**, без ошибки в логе.
- **`@AutoConfigureMockMvc`** живёт в `org.springframework.boot.webmvc.test.autoconfigure`,
  а не в `org.springframework.boot.test.autoconfigure.web.servlet`.
- **Jackson 3** — пакет `tools.jackson.databind`, а не `com.fasterxml.jackson`.

## Что ещё не решено

- **Где живёт объектное хранилище** под Document Vault — вопрос открыт и в
  [infrastructure_architecture.md](../docs/architecture/infrastructure_architecture.md).
  На схеме собственника это «Private Object Storage» внутри закрытого контура.
- **Когда подключаем Keycloak.** По схеме вход строится на Keycloak + MFA, а не
  на своей авторизации; до появления закрытого раздела он не нужен.

Работа ведётся в ветке `back`.
