# Debezium: outbox → Kafka

**Русский** · [English](README.en.md)

Коннектор читает таблицу `outbox` по журналу предзаписи PostgreSQL и кладёт
каждую строку в топик, имя которого совпадает с полем `type`. Приложение
outbox не опрашивает: в режиме `vedal.events.publisher=debezium` relay
не публикует ничего, а события приезжают в `KafkaOutboxListener`.

## Зачем это вместо relay

Relay опрашивал таблицу каждые пять секунд. Задержка события зависела
от периода опроса, а нагрузка на базу — от того, есть события или нет.
Коннектор читает журнал, который PostgreSQL пишет в любом случае: события
уезжают сразу после `COMMIT`, а холостых запросов к базе нет вовсе.

Транзакционный outbox при этом никуда не делся и деться не может. Строка
сущности и строка события по-прежнему коммитятся одним `COMMIT` — иначе
между вставкой и публикацией остаётся щель, в которую проваливаются заявки.
Поменялось только то, кто читает таблицу.

## Настройки, которые нельзя трогать не подумав

| Ключ | Значение | Почему |
| --- | --- | --- |
| `skipped.operations` | `u,d,t` | Потребитель проставляет `published_at` в той же таблице. Без этого его собственный `UPDATE` вернулся бы в топик, `EventRouter` не смог бы его разобрать и засыпал бы лог предупреждениями. |
| `snapshot.mode` | `no_data` | При первом запуске коннектор иначе перечитает всю таблицу и разошлёт всё, что уже было разослано. Повторы отсекутся по `event_consumed`, но смысла в этой работе нет. |
| `route.topic.replacement` | `${routedByValue}` | В `type` уже лежит полное имя топика (`vedal.leads.v1`). Значение по умолчанию добавляет `.events` и уводит события в топики, которых никто не слушает. |
| `table.expand.json.payload` | `true` | `payload` — это `jsonb`. Без разворачивания в топик уезжает строка с экранированными кавычками вместо объекта. |
| `table.fields.additional.placement` | `aggregate`, `correlation_id` в заголовки | Без `correlationId` цепочка запроса обрывается на границе брокера, и письмо перестаёт быть связано с заявкой, которая его породила. |
| `errors.max.retries` | `-1` | База перезапускается — коннектор обязан её дождаться, а не умереть вместе с ней. См. ниже. |
| `retriable.restart.connector.wait.ms` | `10000` | Пауза между попытками. Десять секунд переживают обычный перезапуск базы и не превращают ожидание в цикл без передышки. |

Идентификатор события `EventRouter` кладёт в заголовок `id`. Именно по нему
потребитель отсекает повтор — сообщение без этого заголовка уезжает в DLQ,
а не разбирается «как получится».

## Почему повторы бесконечные

19 августа задача `vedal-outbox-0` умерла от короткого пропадания базы:
`Couldn't obtain encoding for database vedal` → `Connection to db:5432 refused`.
Повторы кончились, и Kafka Connect убил задачу. Сам он упавшие задачи
не поднимает.

Дальше два дня события не уезжали в топики вовсе, и **отказа никто
не видел**: коннектор числился `RUNNING`, контейнер — `healthy`,
в логах портала ни строчки. `FAILED` была только задача внутри
коннектора, и спросить её состояние нужно было руками.

Худшее последствие не в остановке событий. Слот репликации при мёртвой
задаче остаётся неактивным (`pg_replication_slots.active = f`) и держит
WAL, который PostgreSQL не имеет права удалить. Он растёт, пока не кончится
диск, — и тогда встаёт вся база, а не один коннектор.

Поэтому повторов теперь неограниченно: пропавшая база — состояние
временное, а мёртвая задача при живой базе — состояние, которое чинится
только руками и обнаруживается неделей позже.

Заодно проверка здоровья контейнера в `compose.yaml` перестала спрашивать
«отвечает ли REST» и спрашивает «нет ли `FAILED`»:

```bash
curl -s 'http://localhost:8083/connectors?expand=status'
```

## Требования к базе

```
wal_level = logical
max_replication_slots >= 1
max_wal_senders >= 1
```

В `compose.yaml` это задано параметрами запуска PostgreSQL. В облаке —
настройками кластера; у Managed PostgreSQL логическая репликация включается
отдельным флагом, и без него коннектор не поднимется.

Пользователь коннектора должен иметь право `REPLICATION`. В локальном стеке
это владелец базы; в развёрнутой среде заводится отдельная роль — коннектору
не нужны права на запись, и давать их незачем.

## Регистрация

Поднимается контейнером `connect-init` из `compose.yaml`. Руками:

```bash
curl -X PUT -H "Content-Type: application/json" --data @backend/debezium/outbox-connector.json http://localhost:8083/connectors/vedal-outbox/config
```

`PUT .../config`, а не `POST /connectors`: он идемпотентен, и повторный запуск
стека приводит настройку к тому, что лежит в файле, вместо ответа «коннектор
уже существует». Отсюда и формат файла — **только карта настроек**, без обёртки
`{"name": ..., "config": {...}}`: обёртку ждёт `POST`, а `PUT` на неё отвечает
`500` с невнятным сообщением о десериализации. Имя коннектора берётся из адреса.

Состояние:

```bash
curl -s http://localhost:8083/connectors/vedal-outbox/status
```

## Что смотреть, когда события не едут

1. **Лаг outbox.** Метрика `vedal.outbox.lag.seconds`. Отметку `published_at`
   ставит потребитель, когда событие возвращается из топика, поэтому лаг
   меряет весь путь: `COMMIT` → журнал → коннектор → топик → потребитель.
   Растёт — встал какой-то участок, и это главный сигнал.
2. **Состояние коннектора** — `RUNNING` или `FAILED` в `/status`.
3. **Слот репликации.** `select * from pg_replication_slots` — если слот есть,
   а коннектора нет, PostgreSQL копит журнал и однажды кончится место
   на диске. Снятый коннектор нужно снимать вместе со слотом.
4. **DLQ** — топики `<топик>.dlq`. Туда уезжает то, что не разобралось
   после трёх попыток.
