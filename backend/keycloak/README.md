# Keycloak: realm локального стека

**Русский** · [English](README.en.md)

`vedal-realm.json` импортируется контейнером `keycloak` из `compose.yaml` при
первом запуске. Пояснения живут здесь, а не в самом файле: Keycloak разбирает
realm строго и падает на любом поле, которого не знает, — комментарий внутри
JSON уронил бы импорт.

## Что внутри

| Объект | Зачем |
| --- | --- |
| Роли `portal-admin`, `portal-editor` | Обе значат право править содержимое. Разделение на «кто видит» и «кто меняет» появится вместе с CRM, где право видеть сделку и право её менять — разные вещи; заводить его сейчас значит выдумать иерархию, которой никто не пользуется. |
| Клиент `vedal-admin-ui` | Публичный, с PKCE. Секрета у него нет и быть не может: код выполняется в браузере, и любой «секрет» в нём не секрет. |
| Клиент `vedal-portal` | `bearerOnly`. Портал токены не выдаёт — он их проверяет. Клиент заведён затем, чтобы его имя можно было положить в `aud`: без этого токен любого клиента того же realm'а подошёл бы и порталу. |
| Пользователь `editor` | Учётная запись машины разработчика. |

## Про пароль в репозитории

Пароль пользователя лежит в файле открытым текстом сознательно и по тому же
правилу, что пароль PostgreSQL и ключ MinIO в `compose.yaml`: это значения
машины разработчика, они не выходят за пределы docker-сети и никогда
не попадают в развёрнутую среду.

В `prod`, `staging` и `internal` Keycloak поднимается отдельно, учётные записи
заводятся в нём, а этот файл не используется вовсе. Портал в этих средах берёт
адрес realm'а только из переменной окружения — dev-значения по умолчанию там
нет ни у одной настройки подключения.

## Два адреса одного Keycloak

Поле `iss` в токене — это адрес, по которому за токеном ходил браузер, и портал
сверяет его буквально. Забрать по этому же адресу ключи подписи портал в
docker-сети не может: `localhost:8180` изнутри контейнера ведёт в сам контейнер.

Отсюда пара переменных:

```
VEDAL_OIDC_ISSUER=http://localhost:8180/realms/vedal
VEDAL_OIDC_JWKS=http://keycloak:8080/realms/vedal/protocol/openid-connect/certs
```

Первая — что сверять, вторая — откуда брать ключи. `KC_HOSTNAME` в `compose.yaml`
задаёт Keycloak тот же внешний адрес, чтобы он попал в токен.

## Вход

- Админка: `http://localhost:8080/admin/` (через шлюз) или `http://localhost:3000/admin/`.
- Учётная запись: `editor` / `editor-local`.
- Консоль Keycloak: `http://localhost:8180/`, `admin` / `admin-local`.

Токен для curl — прямой выдачей пароля, она включена у клиента для локальной
отладки:

```bash
curl -s -d grant_type=password -d client_id=vedal-admin-ui -d username=editor -d password=editor-local http://localhost:8180/realms/vedal/protocol/openid-connect/token
```

## Второй фактор

Не включён: на машине разработчика он мешает и ничего не защищает. В брифе
собственника MFA числится обязательным, и включается он политикой realm'а
в развёрнутой среде — `Authentication → Required actions → Configure OTP`.
Портала это не касается вообще: он проверяет выданный токен и не знает,
сколько факторов было предъявлено при входе.
