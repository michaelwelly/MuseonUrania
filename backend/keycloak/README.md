# Keycloak: realm локального стека

**Русский** · [English](README.en.md)

`vedal-realm.json` импортируется контейнером `keycloak` из `compose.yaml` при
первом запуске. Пояснения живут здесь, а не в самом файле: Keycloak разбирает
realm строго и падает на любом поле, которого не знает, — комментарий внутри
JSON уронил бы импорт.

## Что внутри

| Объект | Зачем |
| --- | --- |
| Роли `portal-admin`, `portal-editor` | Обе значат право править содержимое. Разделение на «кто видит» и «кто меняет» появится вместе с CRM, где право видеть сделку и право её менять — разные вещи; заводить его сейчас значит выдумать иерархию, которой никто не пользуется. |
| Клиент `vedal-admin-ui` | Публичный, с PKCE. Секрета у него нет и быть не может: код выполняется в браузере, и любой «секрет» в нём не секрет. |
| Клиент `vedal-portal` | `bearerOnly`. Портал токены не выдаёт — он их проверяет. Клиент заведён затем, чтобы его имя можно было положить в `aud`: без этого токен любого клиента того же realm'а подошёл бы и порталу. |
| Пользователь `editor` | Учётная запись машины разработчика. |

## Про пароль в репозитории

Пароль пользователя лежит в файле открытым текстом сознательно и по тому же
правилу, что пароль PostgreSQL в `compose.yaml`: это значения машины
разработчика, они не выходят за пределы docker-сети и никогда не попадают
в развёрнутую среду.

Правило держится ровно на том, что значение локальное, — и ключи от
объектного хранилища под него больше не подпадают. Раньше рядом стоял свой
MinIO, и ключ от него был таким же локальным пустяком. MinIO из стека убран,
хранилище стало настоящим, и тот же ключ теперь открывает бакет, из которого
читает живой сайт. Поэтому `VEDAL_S3_ACCESS_KEY` и `VEDAL_S3_SECRET_KEY`
задаются в `backend/.env`, которого в git нет, а в `.env.example` стоят
пустыми.

В `prod`, `staging` и `internal` Keycloak поднимается отдельно, учётные записи
заводятся в нём, а этот файл не используется вовсе. Портал в этих средах берёт
адрес realm'а только из переменной окружения — dev-значения по умолчанию там
нет ни у одной настройки подключения.

## Два адреса одного Keycloak

Поле `iss` в токене — это адрес, по которому за токеном ходил браузер, и портал
сверяет его буквально. Забрать по этому же адресу ключи подписи портал в
docker-сети не может: `localhost:8180` изнутри контейнера ведёт в сам контейнер.

Отсюда пара переменных:

```
VEDAL_OIDC_ISSUER=http://localhost:8180/realms/vedal
VEDAL_OIDC_JWKS=http://keycloak:8080/realms/vedal/protocol/openid-connect/certs
```

Первая — что сверять, вторая — откуда брать ключи. `KC_HOSTNAME` в `compose.yaml`
задаёт Keycloak тот же внешний адрес, чтобы он попал в токен.

## Вход в локальный стек

- Админка: `http://localhost:8080/admin/` (через шлюз) или `http://localhost:3000/admin/`.
- Демонстрационные пользователи заведены в `vedal-realm.json` и используются
  только на машине разработчика.
- Консоль Keycloak: `http://localhost:8180/`. Пароль администратора генерирует
  `scripts/up.sh` и кладёт в локальный `backend/.env`.

Токен для curl — прямой выдачей пароля, она включена у клиента **только
в локальном realm'е**, для отладки (в `stand/` и `prod/` выключена, см. «Второй
фактор»). Логин и пароль подставьте из своего локального окружения:

```bash
curl -s \
  -d grant_type=password \
  -d client_id=vedal-admin-ui \
  -d username="$VEDAL_LOCAL_USER" \
  -d password="$VEDAL_LOCAL_PASSWORD" \
  http://localhost:8180/realms/vedal/protocol/openid-connect/token
```

## Второй фактор

**На машине разработчика не включён** — здесь он мешает и ничего не защищает:
`vedal-realm.json` не задаёт ни политику паролей, ни защиту от перебора, ни
поток с OTP. Учётная запись `editor` с паролем `editor-local` живёт ровно
поэтому.

**В `stand/` и `prod/` включён и привязан к роли, а не к человеку.** Второй
фактор требуется тому, у кого есть доступ к персональным данным, и решает это
realm-файл, а не память того, кто заводит учётку:

| Роль | Второй фактор |
| --- | --- |
| `portal-admin` | обязателен |
| `portal-sales` | обязателен |
| `portal-production` | не требуется |

Механика — три объекта в realm-файле:

1. Роль `portal-mfa-required`. Прав не даёт; `portal-admin` и `portal-sales`
   включают её композитом, поэтому список «кому нужен второй фактор» правится
   в одном месте, а не по учётным записям.
2. Поток входа `vedal-browser`. Копия встроенного `browser` с единственной
   заменой: в подпотоке `Browser - Conditional OTP` условие
   `conditional-user-configured` («пользователь уже настроил TOTP») заменено на
   `conditional-user-role` с настройкой `condUserRole=portal-mfa-required`.
   Встроенное условие означает «спрашивать код у того, кто его уже завёл», то
   есть не требует ничего ни от кого; условие по роли означает «спрашивать
   у того, кому положено».
3. `browserFlow: vedal-browser` в самом realm'е — иначе поток заведён, но не
   используется.

Форма OTP внутри подпотока стоит `REQUIRED`. Это и есть форсирование: у кого
приложение-аутентификатор не привязано, тот после верного пароля попадает не
в админку, а на экран привязки (`login-actions/required-action?execution=CONFIGURE_TOTP`).

`CONFIGURE_TOTP` в `requiredActions` оставлен с `defaultAction: false`
намеренно: `true` форсил бы привязку **всем** новым учёткам подряд, включая
`portal-production`, которой персональные данные не видны.

**Прямая выдача токена паролем в `stand/` и `prod/` у `vedal-admin-ui`
выключена** (`directAccessGrantsEnabled: false`). Она идёт мимо браузерного
потока — то есть мимо второго фактора — и была бы обходом всего описанного
выше одной строкой curl. Ни админка, ни портал ею не пользуются: админка
ходит по authorization code с PKCE, портал берёт служебный токен по
`client_credentials`. Локальный realm её сохраняет: там второго фактора нет,
и обходить нечего.

Портала это по-прежнему не касается: он проверяет выданный токен и не знает,
сколько факторов было предъявлено при входе.

Порядок включения на живом Keycloak, откат и решение по `/admin` —
[docs/operations/mfa_rollout.md](../../docs/operations/mfa_rollout.md).

## Срок сессии

| Настройка | Значение | Что означает |
| --- | --- | --- |
| `accessTokenLifespan` | 900 (15 минут) | сколько живёт токен доступа; админка продлевает его сама, человек этого не видит |
| `ssoSessionIdleTimeout` | 3600 (1 час) | сколько admin-сессия переживает бездействие |
| `ssoSessionMaxLifespan` | 36000 (10 часов) | предел независимо от активности: рабочий день |

Час простоя — прямое требование: до этого стояло полчаса, а на стенде токен
доступа жил пять минут против пятнадцати локальных. Разъехавшиеся значения —
источник «у меня работает».

**Правка этого файла не меняет уже созданный realm.** `--import-realm`
импортирует realm при первом запуске и дальше существующий не трогает: том
`vedal-keycloak` переживает пересоздание контейнера. То есть на работающем
стенде и на машине, где стек уже поднимался, новые значения сами не появятся.

Два способа их применить:

1. **В консоли Keycloak** — Realm settings → Sessions (SSO Session Idle)
   и Realm settings → Tokens (Access Token Lifespan). Тридцать секунд,
   перезапуск не нужен, ничего не теряется. Это рабочий способ.
2. Пересоздать realm импортом с перезаписью. Так делать не надо без нужды:
   перезапись удаляет realm целиком, а вместе с ним учётные записи, заведённые
   в консоли, — то есть всех сотрудников.

Файл остаётся источником истины для чистой установки: поднятый с нуля стек
получит эти значения сразу.

## Адреса возврата

Keycloak сверяет `redirect_uri` со списком у клиента `vedal-admin-ui` и
сравнивает строки, а не машины. `localhost` и `127.0.0.1` — **разные адреса**,
хотя это один и тот же компьютер. Адрес, которого нет в списке, даёт экран
«We are sorry… Invalid parameter: redirect_uri» ещё до формы входа.

| Realm | Разрешено |
| --- | --- |
| локальный | `http://localhost:8080/*`, `http://127.0.0.1:8080/*`, те же на `:3000` для `next dev` |
| стенд | те же плюс `http://51.250.31.97:18080/*` |

Новая среда — новая строка в `redirectUris` и в `webOrigins`. Пропуск
обнаруживается только при попытке войти, и выглядит как поломка Keycloak,
хотя это настройка клиента.

Проверить, не заходя в браузер:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  'http://localhost:8180/realms/vedal/protocol/openid-connect/auth?client_id=vedal-admin-ui&response_type=code&scope=openid&state=x&code_challenge=abc&code_challenge_method=S256&redirect_uri=http%3A%2F%2Flocalhost%3A8080%2Fadmin%2Fcallback%2F'
```

`302` — адрес принят, `400` — его нет в списке.
